# Rendered-image rerun: CRANE onboard renders through the benchmarked detector

Status: specified, scored only on an existing smoke render. The full set needs Unity renders (one heavy slot at a time)
and a small ground-truth addition in DemoSession, which belongs to the demo/Theater agent.

## Path

1. **Render.** `Crane.Theater.Aerial.DemoCapture.Run` (Editor, `--render` wrapper) with `-demoProfile onboard`.
   - It writes `onboard_oakd_rgb_1080p30.mp4` and `frames.jsonl`.
   - The camera is the OAK-D S2 RGB: 1920x1080, HFOV 69 deg, fx 1396.8 px, onboard volume layer 31.
   - The onboard profile has no cinematic effects: `RenderProfiles.BuildOnboard` throws if any leak in. Motion blur, DoF and grain are off, so blur must come from the sensor model. Set exposure with the obs-model blur, or render at a higher fps and average frames.
2. **Detect.** `Tools/Vision/rendered_rerun.py OUT DEMO_DIR...` decodes the mp4.
   - It runs RT-DETR-R18 tiled 6x640 with tau 0.5 by default (0.3 is also reported).
   - It scores each frame against `person_box_onboard` and compares with `obs_model.p_detect(h, visible, view, blur)`, broken down by height bin.
3. **Compare.** Observed vs predicted rates per case are the sim-to-real check for the observation model. If they disagree, either the renders lack realism (person or clutter appearance) or the model does not transfer.

## Jobs (`Tools/Vision/rerun_jobs.json`, generated by `make_rerun_jobs.py`)

There are 16 variant sequences in `Tools/Vision/rerun_sequences/` (derived from `forest_demo_v1.json`, onboard-only shots, no titles). Each runs with 4 layout seeds (7, 11, 13, 17), giving 64 jobs. Each job is a single `unity-drones --render` call.

| case | what it isolates | from shot |
|---|---|---|
| hover_goldenhour / overcast / dusk | lighting at the 3.2 m stand-off | s5_orbit |
| corridor_v2p0 / v4p5 / v7p0 | speed, so blur at under-canopy range | s3_chase |
| top_30m / top_50m | steep look-down through canopy gaps (the viewpoint NOMAD lacks) | s1_establishing |
| *_empty (all of the above) | the same flights with the person moved 500 m away: false alerts in the rendered forest | |

**Prerequisite (demo owner, Crane.Theater.Aerial).** `frames.jsonl` rows need the following fields:
- `person_box_onboard`: `[x0,y0,x1,y1]` px, top-left origin, from `DemoDirector.PersonBox(rgbCam)`; null when off-screen.
- `person_in_view`
- `person_occluded`
- `person_visible_frac`: the unblocked fraction of N camera-to-person sight rays.
- `person_range_m`
- `cam_yaw_rate`

This is about 15 lines in `DemoSession`'s frame loop. Until it lands, only the `*_empty` cases can be scored.

**Cost.** Each job is about 8–10 s of video. An Editor capture is about 1.5 s warm-up plus render time; the smoke run took 20 frames. Use crf 14, so that H.264 artefacts do not dominate small persons.

## Smoke result (existing render, no GT fields)

`Docs/DroneVisuals/demo/smoke_orbit` (s5_orbit, 20 frames, GoldenHour forest, no person visible in the onboard view by inspection of frame 1694):
- At tau 0.5, **17 of 20 frames carry one detection**, and it is the same object every time: a dark fern silhouette cut off by the bottom edge, box 23x48 px, score 0.50–0.67 (`rendered/smoke_orbit/persistent_fa_crop_f1694.png`).
- This matches the persistent-decoy behaviour measured on NOMAD (80 % of false alerts recur in the next frame).
- The rendered forest already produces the obs model's "decoy" class: 0.85 false alerts per frame here, against 0.14 on NOMAD at tau 0.5. It is one short clip, so treat this as an existence check, not a rate.
